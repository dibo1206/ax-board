# API 절약과 보안 점검

5주차 발표 멘토 피드백 반영 (2026-10-24): "여럿이 쓰는 서버이니 API를 최대한 아끼고, 보안에 신경 쓸 것"

## 1. API를 아끼는 구조

질문 하나가 들어오면 앞 단계에서 끝날수록 AI를 부르지 않는다.

| 순서 | 무엇을 | AI 호출 |
|---|---|---|
| 1 | 건강·환불·대량 구매·주문 조회·배송비 → 정해진 답으로 담당자·기업 문의 | 0회 |
| 2 | 가격·품절·개수·당도 → DB 값 그대로. 추천 → DB 규칙 (조건을 못 찾으면 조건 버튼) | 0회 |
| 3 | 보관·개봉 후·레시피·먹어도 되나·알레르기·산지·수확일·맛·비교 → 품목 정보를 문장 틀에 끼움 (2026-10-26 추가) | 0회 |
| 4 | 같은 질문 + 같은 자료 → 7일 동안 저장해 둔 답. 비슷한 질문 → 담당자 Q&A·최근 AI 답을 글자 비교로 찾아 다시 씀 | 0회 |
| 5 | 그래도 못 찾으면 → 질문 버튼 + 상품 Q&A 안내 (상품과 관련 있으면 [AI에게 물어보기] 버튼) | 0회 |
| 6 | 손님이 [AI에게 물어보기]를 눌렀을 때만 → AI | 질문당 최대 3회 |

질문이 많아져도(하루 500개 이상): AI 호출은 질문 수가 아니라 [AI에게 물어보기]를 누른 수만큼만 는다. 상담용 상품 목록·추천 데이터는 15초 기억해서 질문 500개에 DB 조회가 1,202번 → 106번. 관리자 [상담 기록] 맨 위 **답 못 한 질문**에서 비슷한 질문끼리 묶어 많은 순으로 보고, 위에서부터 품목 정보·Q&A를 채우면 AI 호출이 가장 많이 준다.

측정 (`npm run count-ai`, AI를 부르지 않고 셈): 바꾸기 전 테스트 질문 17개 중 9개가 AI를 불렀다(보관 5·레시피 3·범위 밖 1). 바꾼 뒤 테스트 질문 17개 + 말투 바꾼 질문 18개 = 35개 중 32개를 DB·규칙으로 답했고, 3개(날씨·기분·상품 이름 없는 포장 질문)는 질문 버튼과 Q&A로 안내 — 손님이 버튼을 누르지 않는 한 AI 호출 0회.

호출을 줄이는 장치

- **질문당 최대 3회**: 처음엔 모델 2개까지(붐빌 때 대비), 답이 검사에 걸리면 다른 모델로 1번만 더. 고치기 전에는 최악 8회였다.
- **하루 전체 상한** `AI_DAILY_LIMIT` (기본 40회, 모든 손님 합계): 넘으면 AI를 부르지 않고 "상품 Q&A에 남겨 주세요"로 안내. 가격·품절·당도 질문은 계속 답한다. 무료 키 한도(하루 50회)에서 테스트할 몫을 남겨 둔다.
- **입력 토큰 줄이기**: 앞선 대화는 품목 찾기에만 쓰고 AI에게 보내지 않는다. 전체 상품 목록은 질문에서 품목을 못 찾았을 때만 넣고, 담당자 Q&A는 5개까지.
- **도배 막기**: 같은 IP에서 10분에 상담 15회, 글 남기기 5회. [AI에게 물어보기]는 따로 비회원 10분 3회, 회원 10분 10회.
- **사용량 보기**: 관리자 [상담 기록]에 오늘 AI 호출 수 / 상한, AI 없이 답한 건수.

확인 결과: 같은 질문을 두 번 보내면 AI 호출은 1번 (두 번째는 `cache:` 모델로 기록). 상한에 닿으면 호출 수가 늘지 않고 안내 답이 나간다.

공용 서버의 DB·대역폭도 아낀다 (2026-10-26)

- **DB 연결**: 공용 DB는 계정당 5개. 서버는 3개만 쓰고(`DB_POOL_MAX`) psql·시험 스크립트 몫을 남긴다. 처음엔 10개로 잡혀 있어 관리자 화면이 한꺼번에 여러 요청을 보내면 연결이 바닥났다(`too many connections`) — 고친 뒤엔 요청이 줄 서서 처리된다
- **같은 읽기 한 번만**: 상품 목록·상세는 15초 동안 결과를 기억(`server/cache.js`). 같은 요청 20개가 동시에 와도 DB는 1번 읽는다. 무언가 바뀌면 바로 지운다
- **압축·캐시**: 글자 응답 gzip(목록 8.5KB → 1.7KB), 빌드 파일·사진은 1년 캐시라 다시 들어온 손님은 받지 않는다

## 3. 자사몰 필수 보안 (자체 결제 도입 후, 2026-10-24)

| 항목 | 하는 일 | 확인 |
|---|---|---|
| 비밀번호 | 복호화가 안 되는 해시(scrypt, 계정마다 다른 salt)로만 저장 | DB에 평문 없음 |
| 고유식별정보 | 주민등록번호·계좌번호·카드번호는 **받지 않는다**. 손님이 문의·주문 메모·주소 칸에 주민등록번호나 카드번호(Luhn 검사)를 써 넣으면 저장하지 않고 다시 쓰게 함. AI 상담에서는 가린 뒤 처리 | 주민번호·카드번호 입력 → 400 |
| 저장 암호화 | 이름·전화번호·주소·이메일·배송 메모·사업자등록번호·결제 키·문의 연락처·메일 본문을 AES-256-GCM으로 암호화 (`server/pii.js`). 2단계 인증 키도 같은 방식. 키는 `.env`의 `DATA_KEY` | DB·백업만 유출돼도 평문 없음 |
| 찾기용 값 | 이메일·주문자 휴대폰·사업자등록번호는 HMAC-SHA256으로 따로 저장해서 로그인과 중복 검사에만 쓴다. 키가 없으면 맞춰 볼 수 없다 | 원문 복원 불가 |
| 카드정보 | 토스페이먼츠 결제창이 받고 우리 서버를 거치지 않음 (PCI 부담 최소) | — |
| 관리자 IP 제한 | `ADMIN_ALLOWED_IPS`에 있는 곳에서만 관리자 로그인·관리자 API (판매자는 농가마다 IP가 달라 2단계 인증으로 보호) | 허용 안 된 IP → 403 |
| 2단계 인증 | 인증 앱 6자리 코드(TOTP). `npm run admin-2fa -- 아이디`로 등록, 같은 코드 재사용 막음, 틀리면 잠금 횟수에 포함. `REQUIRE_2FA=1`이면 미등록 계정은 로그인 불가 | 코드 없음·틀림·재사용 → 401, 맞으면 200 |
| 로그인 끊기 | 관리자·판매자 로그인 쿠키를 서명만 믿지 않고 요청마다 DB에서 계정을 다시 확인. 계정을 지우거나 비밀번호·2단계 인증을 바꾸면(`session_version` 증가) 이미 로그인한 쿠키도 바로 끊김. 역할·농가도 DB 값 사용 (2026-10-26, 지운 시험 계정 쿠키가 계속 통하던 문제를 찾아 고침) | 비밀번호 변경·계정 삭제 뒤 예전 쿠키 → 401 |
| 접속 기록 | 관리자·판매자의 로그인·실패·로그아웃과 모든 요청(계정·역할·일시·IP·주소·결과)을 `access_logs`에 남김, 요청 본문은 남기지 않음. 관리자 [접속 기록]에서 확인. 1년 이상 보관 | 로그인 실패·성공·요청·로그아웃 기록 |
| 결제 금액 위변조 | 승인 전에 결제창에서 돌아온 금액과 서버가 계산한 주문 금액이 같은지 확인, 토스 승인 결과도 다시 확인. 다르면 승인하지 않고 주문 실패·재고 복구. 옵션 상품은 화면이 보낸 값이 아니라 DB 옵션 가격으로 계산 | 1만 원 낮춘 금액 → 400, 주문 실패 |

## 5. 배포할 때 할 일

- HTTPS(개인정보 전송 암호화), `NODE_ENV=production` (쿠키 Secure), `PUBLIC_URL`, 프록시 수에 맞게 `TRUST_PROXY_HOPS`
- `npm run build` → `npm start`(서버 하나가 화면 + API). 이때는 이 서버가 맨 앞이라 `PROXY_SECRET` 검사를 하지 않는다. 화면 서버를 따로 두는 구조면 그 서버가 `PROXY_SECRET` 머리글을 붙이게 설정
- `REQUIRE_2FA=1`, `ADMIN_ALLOWED_IPS`에 회사 사무실 IP, 모든 관리자·판매자 계정 2단계 인증 등록
- 접속 기록은 지우지 말고(1년 이상, 고유식별정보를 다루면 2년) 정기적으로 따로 백업해 위변조를 막기
- 개발 중에는 모두가 SSH 포트 전달로 들어와 같은 IP(127.0.0.1)로 보인다. 그래서 횟수 제한과 로그인 잠금을 함께 받는다. 배포하면 실제 손님 IP로 나뉜다
- 상담 기록·문의 연락처 보관 기간을 기업과 정하고, 지난 기록은 지우기
- DB 백업
- 자동 재시작(pm2·systemd): 예상 못 한 오류가 나면 서버가 안전하게 꺼지도록 했으므로, 꺼지면 다시 켜 주는 관리 도구가 필요
- `/api/health`를 모니터링에 연결 (DB까지 살아 있으면 200, 아니면 503)

| 개발 서버(Vite)가 `/@fs/절대경로` 로 서버 코드·`data/` CSV·`vite.config.js`·`deploy/` 를 보여 줌 | 같은 실습서버의 다른 사용자(약 50명)가 포트로 접속해 팀 데이터·코드를 읽음 (홈 폴더 권한 750을 우회) | 주소를 실제 파일 위치로 바꿔 보고 화면용 폴더(src·public·node_modules)와 index.html 밖이면 404 | 10개 경로 모두 404, 화면·HMR 정상 |
| 결제 안 하는 주문으로 재고 묶기 | 주문하면 결제 전 30분 동안 재고를 잡아 두는데, 상품당 99개·10분에 10건까지 가능해 재고를 전부 묶을 수 있었음 | 상품당 20개·주문당 60개, 같은 휴대폰 번호로 결제 안 한 주문 3건까지, 같은 IP 30분에 6건(운영) | 21개·61개 → 400, 4번째 미결제 주문 → 429, 7번째 주문 → 429 |
| 다른 사이트가 몰래 보내는 요청(CSRF) 이중 방어 | 쿠키 SameSite=Lax 만 있었음. 같은 도메인의 다른 하위 사이트가 뚫리면 관리자 쿠키로 요청 가능 | 바꾸는 요청(POST·PATCH·DELETE)은 브라우저가 붙이는 Origin 이 우리 주소일 때만 | 남의 Origin → 403, 비슷한 이름(`…3066.evil.com`) → 403, 우리 화면 → 200 |
| 로그인 응답 시간으로 가입 여부 알아내기 | 없는 아이디는 비밀번호 계산을 안 해서 더 빨리 답함 | 없는 계정도 가짜 해시로 한 번 계산 | 있는 아이디 0.031초 / 없는 아이디 0.027초 (차이는 네트워크 수준) |

| 비밀번호 재설정 링크가 기록에 남음 | 메일 설정이 없으면 링크를 서버 기록에 출력 | 운영(NODE_ENV=production)에서는 출력 안 함, 화면은 링크의 토큰을 읽자마자 주소창에서 지움, `referrer` same-origin | — |

다시 확인해서 문제없던 것

- SQL: 손님 입력은 모두 `$1` 자리표시로만 넣는다. 문장에 끼우는 건 코드에 정해 둔 조건(정렬·카테고리)뿐
- 화면에 HTML로 그리는 곳 없음(`dangerouslySetInnerHTML` 0), 메일은 글자만. 검색엔진용 HTML 은 모두 이스케이프, JSON-LD 의 `<` 처리
- 모든 관리자·판매자·회원 API 에 문지기(requireAdmin·requireSeller·requireCustomer). 판매자는 자기 농가 상품·주문만, 회원은 자기 주문만
- 관리자·판매자 로그인은 요청마다 DB 확인(계정 삭제·비밀번호·2단계 인증 변경 시 바로 끊김), 쿠키 HttpOnly·SameSite=Lax·운영에서 Secure
- 사진: jpg·png·webp 2MB, sharp 로 다시 만들어 숨은 코드·위치 정보 제거, 4천만 픽셀 넘는 '압축 폭탄' 거절, 우리가 만든 파일 이름만 지우기, 사진 주소는 스크립트 실행 금지(CSP sandbox)
- 결제: 금액은 서버가 계산하고 승인 전·후 두 번 확인, 비밀키는 서버에만. 빌드된 화면 파일에 PROXY_SECRET·AI 키 0건
- 저장소에 비밀값 커밋 0건, `.env` 권한 600, 홈 폴더 750, `npm audit` 취약점 0건
- 개인정보: 주민번호·카드번호 입력 거절, AI 상담·기록 전 연락처 가림, 비밀번호 찾기는 가입 여부와 관계없이 같은 답

남은 위험과 선택

- 회원·관리자가 로그아웃해도 그 전에 훔친 쿠키는 만료(회원 7일·관리자 8시간)까지 쓸 수 있다. HttpOnly 라 화면 스크립트로는 못 훔치지만, 공용 PC 사용 후에는 비밀번호 변경(모든 기기 로그아웃) 안내
- 가입할 때 "이미 가입한 이메일"이라고 알려 준다(대부분의 쇼핑몰과 같음). 가입 시도는 같은 IP 1시간 5번
- 관리자 계정을 5번 틀리면 10분 잠긴다 → 일부러 틀려 관리자를 잠그는 방해가 가능. 운영에서는 `ADMIN_ALLOWED_IPS` 로 사무실에서만 로그인되게 해서 줄인다
- 횟수 제한은 서버 메모리 기준이라 서버를 다시 켜면 초기화된다(서버 1대 운영에선 충분)
- 실습서버는 같은 서버의 다른 사용자가 포트에 접속할 수 있다(구조상 한계). 실제 손님은 운영 서버(docs/deploy.md)로

## 7. AI 상세 내용 초안도 아끼고 거르기 (2026-10-27)

- 상품당 한 번만 부른다: 같은 입력 + 같은 상세페이지 패턴이면 저장된 초안(30일, AI 0회). 계정마다 1시간 20번, 하루 전체 상한 `AI_DAILY_LIMIT` 안에서
- 같은 원물의 보관법·레시피는 품목 정보로 재사용 → 비어 있을 때만 AI 가 만든다. 품목 정보는 비어 있는 칸만 채우고 덮어쓰지 않는다
- 초안에서 금지어 사전에 걸린 문장, 입력에 없는 숫자를 쓴 문장은 빼고 알려 준다. 판매자가 검토·저장해야 공개(저장할 때 다시 금지어 검사)
- 자주 묻는 질문은 상담 챗봇의 비슷한 질문 찾기에 들어가 AI 호출을 더 줄인다
- 금지어 사전은 관리자만 고칠 수 있다(판매자 403). AI 를 부르지 않는 검사라 비용 0
